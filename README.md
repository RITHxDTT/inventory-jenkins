# Stockroom — Inventory Management

A server-rendered Django inventory system with PostgreSQL, Tabler (Bootstrap 5), Bootstrap Icons and Chart.js. Products, categories, suppliers, accounts, permissions, stock movements, reports and audit logs use real database records.

## Start in this workspace

Your existing `venv` and PostgreSQL Compose service are used. A local `.env` with a generated secret has been created. The database password matches your existing development Compose configuration.

```bash
source venv/bin/activate
docker compose up -d
python manage.py migrate
python manage.py seed_data
python manage.py runserver
```

Open **http://127.0.0.1:8000/**. Development demo accounts:

| Username | Password | Access |
| --- | --- | --- |
| admin | DemoStock!2026 | Full application administration and Django admin |
| manager | DemoStock!2026 | Catalog, stock, dashboard and reports |
| staff | DemoStock!2026 | Catalog viewing, stock in/out and transaction history |

These credentials are for local demonstrations only. `seed_data` requires `APP_DEBUG=True`, does not reset existing passwords, and does not duplicate products or their opening movements. It restores default role permissions. Do not seed a deployed system.

## Fresh installation

Requires Python 3.12+ and PostgreSQL 17 (Docker recommended).

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Replace `SECRET_KEY` in `.env` with a long random value, for example generated by `python -c "import secrets; print(secrets.token_urlsafe(48))"`. Configure `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, and `DB_PORT`. The sample credentials match the provided local Compose service; use separate credentials for deployment.

`APP_DEBUG` controls Django development mode. The explicit name avoids conflicts with generic `DEBUG` environment variables set by IDE tools. Process environment variables take precedence over `.env`.

```bash
docker compose up -d
python manage.py migrate
python manage.py setup_roles
python manage.py createsuperuser
# Optional development sample data:
python manage.py seed_data
python manage.py runserver
```

Migrations are committed; `makemigrations` is only needed after modifying models.

## Features and workflows

- Django session login, POST logout, password change, email password reset and profile image uploads.
- User creation, editing, role/direct permission assignment and activation/deactivation. Historical users cannot be deleted in the application or admin.
- Manage roles and permissions through Accounts → Roles. User and group administration are powerful privileges: only grant them to trusted administrators.
- Product/category/supplier creation, details, editing and confirmation-based archival. Archives preserve relationships and stock history. Archived product quantities remain part of physical inventory totals.
- Unique SKU, nonnegative prices and stock limits; product quantities cannot be edited in product forms or Django admin.
- Receive/issue stock using positive integer quantities. Stock out requires a reason. Every movement records the actor, reference, date, notes and before/after quantities.
- PostgreSQL row locks and atomic transactions serialize movement requests; failed movement or audit creation rolls back the entire operation.
- Search, filters, sorting and server-side pagination. Lists use server-side controls rather than layering client pagination over a partial dataset.
- Current inventory, low-stock, out-of-stock, inbound, outbound, movement and value reports. Date ranges refer to the business transaction date; creation timestamps preserve the actual recording time.
- Monetary amounts are displayed in USD and calculated with Decimal. Inventory value equals quantity × cost price. Low stock means `0 < quantity <= minimum`; out of stock means quantity is zero.
- Immutable transaction/audit admin screens and logged catalog changes. Corrections use a compensating stock movement with a reference to the original; existing history is not edited.
- Responsive Tabler layout and database-backed charts. Tabler bundles Bootstrap 5. Frontend assets load from pinned public CDNs, so the browser needs internet access for styling and charts.

## Email and uploads

Development password-reset emails print to the server console. For real delivery set `EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend`, `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`, and `DEFAULT_FROM_EMAIL` in the environment. Reset requests do not reveal whether an account exists.

Images must be JPEG, PNG or WebP, at most 5 MB and 20 million pixels. Development serves media through Django. Production must serve `media/` separately as untrusted uploaded content, and persist it across deployments.

## Verification

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python -m pytest -q
python manage.py collectstatic --noinput
```

Tests use a separate PostgreSQL database (`test_inventory_db` by default). The configured test database user needs permission to create/drop this test database. Tests cover page rendering, access control, CRUD, login/logout/reset, stock balances, invalid quantities, rollback, archival, uniqueness, report values and PostgreSQL concurrency.

## Project structure

- `config/`: environment-driven settings, URL routing, WSGI/ASGI.
- `accounts/`: profiles, user/role management, setup and demo commands.
- `inventory/`: catalog and movement models, forms, filters, atomic stock service.
- `suppliers/`: supplier records and screens.
- `reports/`: dashboard queries and Decimal report calculations.
- `audit/`: administrative audit records and viewer.
- `common/`: reusable CRUD, pagination, form styling, image validation and admin policies.
- `templates/`, `static/`: shared dashboard UI, authentication, reports and charts.
- `tests/`: pytest-django integration and business-rule tests.

## Production

Set a unique `SECRET_KEY`, `APP_DEBUG=False`, appropriate `ALLOWED_HOSTS`, real database and SMTP credentials. HTTPS redirects and secure session/CSRF cookies are enabled outside development. Terminate HTTPS at your reverse proxy and configure trusted proxy headers only for your deployment topology. Run `python manage.py check --deploy` and configure HSTS according to your domain rollout.

```bash
python manage.py migrate
python manage.py collectstatic --noinput
gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 3
```

A Dockerfile is included. The existing Compose file intentionally runs the database; to run the web image, supply environment variables (including a database host reachable from its container), persist media, and run migrations/collectstatic before starting Gunicorn. The image excludes `.env`; runtime secrets are supplied externally. WhiteNoise serves collected static assets.
